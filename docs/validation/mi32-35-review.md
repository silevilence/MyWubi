# MI-32～MI-35 验收记录

日期：2026-11-06。环境、模型哈希和逐次结果保存在 [mi32-35/](mi32-35/)。
用户确认暂无 NVIDIA 与 Android ARM64 设备，相关实测保持待办。

## MI-32 Vulkan

本机 Windows 11 / Core Ultra 7 165U / Intel Graphics 驱动 32.0.101.8425，
Vulkan 实际发现 `Vulkan0`（统一内存）。通过独立 model-worker 完成设备发现、
GGUF 加载、预热、预测、暂停释放与恢复。只覆盖这一个 Intel 驱动/设备组合，
不推断 AMD、NVIDIA、独显、Windows ARM64 或其他驱动兼容。

模型为 Qwen2.5-0.5B-Instruct Q4_K_M，权重 SHA-256
`74a4da8c9fdbcd15bd1f6d01d621410d31c6fc00986f5eb687824e7b93d7a9db`；
使用原有 `qwen25-short-words-v1` 适配与准入策略，三个固定公开前文，不读取用户输入。

| 测量 | CPU | Vulkan |
| --- | ---: | ---: |
| 后续进程原生 load | 875 ms | 1064 ms |
| warmup | 656 ms | 262 ms |
| 北京 | 283 ms，市/区/县 | 246 ms，市/区/县 |
| 明天去 | 318 ms，出差/探亲/休假 | 211 ms，出差/探亲 |
| 我想喝 | 65 ms，Empty | 243 ms，水/茶/咖啡 |
| drop | 92 ms | 118 ms |

这是三个样例的适配器对照，不是质量或分位性能结论。输出有差异，不宣称 GPU
更准确，也不因此改变默认 CPU。原始首次驱动运行的 warmup 为 20.6 s、前两次
预测为 5.58/6.48 s；保留在 `vulkan-first-driver-run.jsonl`，没有删掉冷启动成本。
首次运行与生命周期测试时有构建后台负载，因此这些耗时只证明闭环，最终性能
对照须用稳定制品、单独运行再测。

`vulkan-lifecycle.jsonl` 记录独立进程 Ready、首两次超时隐藏、后续 261 ms 内返回、
Paused、恢复 Ready。超时不延长 1000 ms 配置预算、不补发旧结果。
`missing-device.jsonl` 证明请求不存在的设备保留请求信息并在 CPU 成功预测。
自动测试另覆盖设备/后端/显存匹配、可恢复执行失败释放 GPU 后重试 CPU，以及
超时/取消/低置信度不触发回退重算。未强行重置用户显卡驱动来制造真实设备丢失；
原生进程级崩溃不算可恢复 Rust 错误。

构建：固定 llama-cpp-2/sys 0.1.161，Vulkan SDK 1.4.363.1，VS C++ + Ninja；
纯 CPU workspace check、120 项核心/模型单元测试、相关严格 Clippy、Android
`:app:compileDebugKotlin` 通过。SDK 的普通安装因需要提权而回滚，随后按官方支持
的 copy_only 模式将开发文件复制到工作区，没有修改系统权限或安装显卡驱动。
MSBuild ExternalProject 步骤乱序问题通过构建脚本使用 Ninja 解决。

可选组件经 `stage_gpu_component.ps1` 和
`python scripts/check_model_artifacts.py --gpu-dir target/mi32-component` 验证：PE x64、
运行特性 Vulkan/llama/ORT、26 个文件哈希/大小、10 份许可证哈希、无模型权重。
终端用户不需 SDK；Vulkan loader/驱动由系统与厂商提供。独立 CPU 组件继续可构建。
自动组件分发仍由 MI-36～MI-39 承担。

## MI-33 CUDA 与 MI-34 ONNX 决策

CUDA feature、共用回退路径、显式 SM 构建和组件依赖/许可检查已提交；本机没有
NVIDIA GPU 或 CUDA Toolkit，未构建 CUDA 二进制，未验证可分发 CUDA 组件。
`cuda-unavailable.jsonl` 记录请求 CUDA 后在 CPU 返回结果，不能代替 CUDA 执行
验收。MI-33 及相关子项保持未完成，按用户要求保留设备验收待办。

MI-34 按任务允许的“接入或暂缓决策”完成评估，详见
[ONNX GPU 决策](../model-input-onnx-gpu-decision.md)。现有计数/随机图不能支持
真实产品模型的收益结论，因此保留 CPU；GPU 实施与产品模型对照子项仍未完成。

## MI-35 测量方法与短测

最终制品采用 release / Vulkan + ORT；每次 `.meta.json` 记录 worker/probe 的
SHA-256，同组测量复用同一制品，未并行运行本任务的编译或其他基准；未隔离系统
后台任务。配置均为候选上限
3、CPU 线程 2、1000 ms 等待预算，固定循环“北京 / 明天去 / 我想喝”，沿用相同
模型、量化、分词器、生成和准入策略。样例为人工编写的公开测试文本，不是独立
质量集，不改变 MI-26 的模型尚未通过质量验收结论。
每次请求结束后间隔 100 ms；持续测量表示该节奏下连续运行，不是实际键盘输入
或 GPU 满负载烤机。进程冷启动未清除操作系统文件缓存或驱动着色器缓存。

`probe-pipeline` 使用真实共享 Session 提交确认、当前用户命名管道、独立
model-worker 以及共享候选发布路径。`visible` 指共享候选已经可发布，**不包含
真实 TSF 编辑回调、GDI 绘制、屏幕扫描或人工观感**。因此真实屏幕首次可见预测
仍待补验，不能将本表当作完整桌面端到端延迟。各次创建新会话，避免继承前文。

最终短测每后端 60 次，下面的热态分位去掉首个请求，仅统计有效候选发布，采用
nearest-rank；无候选和超时进入比例分母。原始记录为 `cpu-final.*` 与
`vulkan-final.*`，自动汇总工具还按前文拆分统计，避免条件样本混合造成误读。

| 指标 | CPU | Intel Vulkan |
| --- | ---: | ---: |
| 进程启动至预加载就绪（含校验、加载、预热） | 2208 ms | 2226 ms |
| 就绪后首次候选发布 | 296 ms | 305 ms |
| 热态有效候选 P50 / P95 / P99 | 356 / 463 / 472 ms | 254 / 280 / 282 ms |
| 热态超时 | 0 / 59 | 0 / 59 |
| 热态有效展示 | 39 / 59（66.1%） | 59 / 59（100%） |

CPU 的“我想喝”返回 Empty；Vulkan 返回“水/茶/咖啡”。“明天去”的候选数量
也不同，只有“北京”的“市/区/县”在这组样例上一致。**没有证明同等预测质量
下的 GPU 净收益**，不因更高展示率就称为更准确。先前 `*-pipeline.*` 的中间
制品结果完整保留，其中 Vulkan 曾有 2 / 59 热态超时；不把中间制品与最终制品
拼成同一统计组，也不删除失败样本。首次驱动编译成本见上方 MI-32 记录。

仅取输出相同的“北京”热态子组，各 19 次，CPU P50 / P95 / P99 为
343 / 472 / 472 ms，Vulkan 为 259 / 282 / 282 ms。这是一个前文的小样本加速
证据，不能推广为全部预测的同质量收益。两组短测工作集峰值分别为
508.4 / 915.2 MiB，私有字节峰值为 482.9 / 955.7 MiB；Vulkan 另报告
813.2 MiB GPU 共享内存。Intel UMA 的这些数值有共享映射，不能简单相加当作
物理内存总占用。GPU 计数器是该进程各引擎利用率的最大值，CPU 百分比以单核
100% 计；都不是整机功耗。

`cpu-cold-final.*` / `vulkan-cold-final.*` 的按需模式首个请求均在约 1003 ms
后隐藏，不能在首次输入预算内完成加载；后续请求可以发布。其 prepared 事件
仅代表配置已交给服务，actual 为 null，不代表模型已就绪。这也是建议主动启用
模型的用户采用提前加载的依据；预测本身仍默认关闭。

自动模式有预加载/电源/内存准入、同输出与超过 15% 收益门槛，详见
[自动策略](../model-input-gpu.md#自动选择与默认策略)。`auto-final.*` 实测用
3135 ms 到达就绪，实际为 CPU，原因为 CPU 短基准存在无结果样例。按需自动模式
跳过筛选、保留 CPU，`auto-cold-final.*` 保留首次请求的超时结果。筛选不是质量
认证，也不承诺动态功耗优化或跨次加载缓存；用户仍可手动选择受支持设备。

## MI-35 连续运行与资源

`vulkan-stability.*` 完成 1800.125 秒连续请求，共 4727 次，进程正常结束并记录
closed 事件。去掉首个请求后 4726 / 4726 次在预算内发布，超时为 0，热态有效
发布 P50 / P95 / P99 为 **272 / 317 / 342 ms**。这是本机、当前驱动和三个固定
前文下的 30 分钟共享链路稳定性结果，不是跨设备稳定性或预测质量通过。

| 持续运行窗口 | 热态请求数 | P50 / P95 / P99 |
| --- | ---: | ---: |
| 首五分钟 | 823 | 264 / 286 / 300 ms |
| 末五分钟 | 763 | 286 / 326 / 349 ms |

末段 P95 比首段约高 14%；没有温度/功率数据，不能断定原因是温控、频率变化
或系统后台活动。完整统计与分前文结果由 `report_device_comparison.py` 从原始
记录生成，短测和长测分开列出，不用短测的更好数字代替持续运行结果。

Vulkan 空闲驻留窗口约 8 秒、3 个资源样本：工作集中位 909.9 MiB、私有字节
950.3 MiB、GPU 共享内存 811.5 MiB，GPU 引擎占用为 0%。持续运行首分钟与
末分钟的私有字节中位分别为 955.7 / 956.0 MiB，GPU 共享内存均为 813.2 MiB，
未观察到持续增长。全程 CPU 单核百分比中位 38.3%，GPU 引擎最大占用中位 52%，
其采样峰值为 89%。工作集受系统修剪影响，末段下降不能等同于模型已释放。

Close 事件只确认服务不再报告活动执行设备；测试程序随后结束自己创建的工作
进程，不能把这一时刻伪称为原生异步析构已经完成。原生自然 drop 耗时另由
MI-32 的 `probe-device` 记录。未执行 CPU 的另一组 30 分钟长测，不宣称两后端
已经完成同样时长的热稳态对照；CPU 另补空闲/连续短驻留采样。

`cpu-residency.*` 在 Vulkan 长测结束后串行采集，先空闲 10 秒，再执行 60 次
请求（36.7 秒）。空闲工作集中位 508.4 MiB、私有字节 482.9 MiB，持续请求时
私有字节中位 483.0 MiB；CPU 单核占用中位从空闲 0.65% 升至持续请求 145.0%。
该次热态有效发布 P50 / P95 / P99 为 658 / 896 / 979 ms，1 / 59 超时、
38 / 59 有效发布，明显慢于之前的 CPU 短测。没有控制后台任务、热状态或读取
到温度，不能给出确定原因，也不能挑掉这组较慢结果；它与之前短测分开保留。
这进一步限制了“同条件净收益”的结论，默认和自动模式继续保守采用 CPU。

全部最终组汇总见 [final-summary.json](mi32-35/final-summary.json)；组别、哈希和
统计边界见 [证据索引](mi32-35/README.md)。最终 Vulkan 可选组件已重新生成并
通过运行能力、26 文件哈希/大小和 10 份许可核验，清单见
[vulkan-component.json](mi32-35/vulkan-component.json)。

## 回归与验收边界

[checks.json](mi32-35/checks.json) 记录验证日志摘要与哈希：workspace 测试
359 通过、0 失败、3 忽略；最终 Vulkan/ORT 原生库单元测试 34 通过、0 失败、
1 忽略。CPU 与 Vulkan/ORT 的相关全目标严格 Clippy 通过，Android Kotlin 编译
通过。另有报告计算测试 2 项通过，覆盖分位、超时分母、缺测值和不完整运行。
忽略项没有算作通过，Kotlin 编译不代表 Android 设备验收。

整体审核核对了默认 CPU 与旧配置、平台边界、设备请求/实际状态、可恢复错误与
截止时间、组件许可和证据统计。未把 GPU 运行库链接进 TSF DLL，未改模型准入、
默认开启状态或用户宿主输入数据记录策略。

仍需补验：NVIDIA 原生构建/组件/真机，Android ARM64 的冷/热响应、功耗、温度
和持续运行，以及真实 TSF 宿主至屏幕绘制的最终可见延迟。Windows 温度接口返回
拒绝访问，未提升权限重试；没有校准的功耗提供器，功耗/温度保留 null，见
[power-availability.json](mi32-35/power-availability.json)。电池电量读数不充当
耗电测量。用户确认暂无额外设备，相关待办保持未勾选。
