# MI-24 / MI-25 模型准备与资源生命周期

## 策略

`prediction.loading` 缺省为 `on_demand`，旧配置仍按需加载。`preload_keep`
只有在预测开启且选定模型时生效。Windows 保存设置、TIP 激活会发送后台准备；
Android 在允许输入的 IME 生命周期中准备。两端界面提供相同配置字段。
预热只使用固定的“预热完成”测试文本，随后清除推理状态，不读取宿主文本。
`Loading` 包括权重加载、上下文初始化和短预热；完成后才报告 `Ready`。
原生加载不能强行中断；准备有独立 30 秒预算，退出/配置版本变化使旧工作失效。

Windows 继续使用每用户的独立单实例服务；`Prepare` 不抢占输入会话所有权。
跨应用只共享模型权重，切换所有者清除待发布结果与推理缓存。保持模式不因
10～600 秒的普通空闲卸载；关闭、无模型、暂停或系统低内存通知释放模型。
低内存结束后可重新准备，显式暂停不被低内存恢复覆盖。服务异常后下一次
新请求重新拉起进程；再次激活也重新准备。没有后台无限重启循环。
保存完成后先同步创建独立的无窗口服务进程，将已保存配置路径交给它；原生加载和 IPC 重试在该进程中完成，不依赖设置窗口继续存活。

Android 隐藏/失焦/敏感输入暂停并释放；重新显示后按已保存策略重建。
服务销毁关闭工作器；连接改变撤下旧会话请求。低内存、严重热状态、节电及
未充电低电量暂停；前台允许期间每秒重查资源状态，隐藏时停止轮询。
系统 `onLowMemory` / `onTrimMemory` 主动暂停，下一次允许的生命周期或输入事件恢复。
预加载不意味着 Android 后台永久驻留。

## MI-24 修复后的验收

根因是原先由设置进程的后台线程承担服务启动和重试，窗口保存后立即退出会终止尚未完成的交接。现由 `model-worker --config PATH` 自己读取已原子保存的配置；已存在服务则转交 Prepare，没有服务则竞争单实例所有权并按已保存策略准备。设置 UI 只启动独立进程，不等待权重加载。配置为关闭/无模型/按需且没有既存服务时，转交进程直接退出。

[真实设置保存退出测试](validation/mi24-final-handoff.log)从 `AppState::load/save` 发起保存并立即退出进程，约 2.75 秒后服务 Ready；随后不轮询地空闲 61 秒，仍为同一 Ready PID。关闭保存后为 Idle，再启用后同一服务重新 Ready，未创建每宿主模型实例。[崩溃与重新激活测试](validation/mi24-final-crash.log)终止该测试创建的服务，新请求入队不超过 100 ms；新 PID 就绪后新版本请求成功，重新创建客户端仍复用新 PID。

[真实后端的资源压力回归](validation/mi-final-generation-session.log)通过生产 OS 监视器调用的 `Endpoint::resource_pressure` 边界触发释放和恢复，验证旧请求/结果不再发布、恢复后新请求返回“市”、关闭后解除压力不会重新加载。这里主动触发的是生产回调，并未实际耗尽开发机内存；Windows 新会话验证来自全新 Sandbox 中的服务与真实记事本，不把客户端重建说成真实开发机注销/登录。

CPU 两线程、Q4_K_M 原权重与原策略、1000 ms，停止全部构建和 Android 模拟器后顺序测量，自编前文“明天去”：

| 策略/场景 | 最终观测 |
| --- | --- |
| 保持模式准备到 Ready | 2096 ms |
| 保持模式首次 / 热请求 / 空闲 11 秒后 | 430 / 425 / 359 ms，均返回出差、探亲、休假 |
| 保持模式暂停后重新 Ready | 2168 ms |
| 按需首次冷请求 | 预算内无结果，正常回退；探针到 1111 ms 结束观察 |
| 按需 Ready 后新请求 | 376 ms，成功返回三个候选 |
| 按需空闲超过 10 秒后 | 权重卸载，再次冷请求回退 |

原始记录：[保持](validation/mi24-final-preload-keep.jsonl)、[按需](validation/mi24-final-preload-demand.jsonl)。探针已修正：按需的“热请求”必须等 Ready 后重新发起，不能将仍在冷加载队列中的第二次请求误称热请求；[原探针失败记录](validation/mi24-demand-before-ready.jsonl)未删除。1111 ms 等数字是探针观察时长，不表示允许产品发布超过 1000 ms 的结果。

[驻留采样](validation/mi24-final-loaded-memory.json)工作集约 481.4 MiB、私有内存约 450.7 MiB；[原生工作结束后释放采样](validation/mi24-final-released-memory.json)约 11.4 / 5.8 MiB。关闭请求不会强行中断原生权重加载，[关闭 300 ms 时仍加载的瞬时采样](validation/mi24-final-close-transient-memory.json)仍占内存；旧工作不能发布，完成后才释放。进程工作集并非精确模型分配量。


提交前补充了“设置预热后普通宿主的首个请求”回归，发现 `canonicalize` 给 Windows 配置路径加上 `\\?\` 前缀，导致同一目录以普通路径到达时被当作新模型目录重新加载。[修复前](validation/mi24-host-path-before-fix.log)服务虽 Ready，首个普通宿主请求 1005 ms 后仍为空。服务启动现在保留调用方绝对路径写法，相对路径仅拼接当前目录；[修复后](validation/mi24-host-path-after-fix.log)相同首请求约 217 ms 返回“市”，后续 61 秒驻留、关闭再启用继续由同一测试覆盖。测试异常时也恢复专用配置并结束测试创建的服务。
